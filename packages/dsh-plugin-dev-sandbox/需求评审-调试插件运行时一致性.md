# dsh-plugin-dev-sandbox：调试插件运行时一致性需求评审

- 状态：需求评审稿，待确认
- 日期：2026-11-12
- 目标包：`packages/dsh-plugin-dev-sandbox`
- 问题场景：在开发另一个含 Host service 和 Client UI 的插件时，调试实例需要看到与该实例一致的模型目录，且不得触碰宿主全局配置。

## 1. 评审结论

建议通过，作为一次**沙箱插件运行时组装缺陷修复**立项。核心目标是使被调试插件的 Host 端、Client 端及其远程服务都在同一个沙箱 DSH 实例工作，并让插件只通过当前运行时公开的 `llm` 服务读取模型目录。

维持会话级隔离：外层宿主负责启动、停止和管理沙箱；沙箱 DSH 自己加载被调试插件，并提供被调试插件使用的 `llm` 服务。不得为了让插件看到模型而更改宿主 profile、从宿主向浏览器暴露秘密、或令插件直接读取 `models.json`、overlay 或 credentials 文件。

当前需求材料给出了目标架构和风险偏好，但尚未提供可重现步骤、实际错误提示或日志。因此本评审把“完整插件上下文未进入沙箱”登记为**待验证根因**，不能在实现前宣称已经证实。

## 2. 当前行为与问题

从当前实现和包文档确认：

- 沙箱按当前 DSH 会话和工作区绑定插件包；每会话使用 `.dsh/plugin-dev/<sessionId>/runtime` 作为独立 `DSH_HOME`。README 明确说明这属于 profile/进程隔离，不是 OS 安全沙箱，本地插件代码仍以当前用户权限运行。
- 模型面板的目录由沙箱插件外层 Host 的 `llm.listProviders()` 与 `llm.listModels(provider)` 读取；选中模型随后被转换为配置 overlay，凭据在 Host 侧解析后写到沙箱 runtime 的 `.credentials.yaml`。
- `backend/manager.js` 的 overlay 组装目前插入一个以被调试插件主入口 `file://` URL 命名的插件行，另有模型 settings patch；没有显式组装/验证其 Client manifest 注入、Client bundle 注册及所需 Host service 的可用性。
- `model-intelligence-test` 的 Host `ModelIntelligenceService.catalog()` 从其所处运行时的 `llm` 读取目录；Client 通过 `remote.modelIntelligence` 调用该服务。其包清单另声明 Client 入口和 sidebar 注入。
- 因此模型选择面板看到外层 Host 的目录，不足以证明沙箱内 Composer、沙箱设置页和被调试插件的 Host service 使用的是同一份有效目录。被调试插件的 Client 是否进入沙箱 boot manifest、远程调用是否连接沙箱中的 Host service，也必须通过实际运行时验证。

可能的用户可见后果：插件没有出现在沙箱 UI、右栏入口存在但远程服务不可用、目录错误被错误映射为数据格式问题，或者调试结果与沙箱 Composer/设置页面看到的模型不同。

## 3. 目标与非目标

### 目标

1. 沙箱中的被调试插件作为完整的 DSH 插件运行：Host 入口、Client 入口/依赖注入和远程服务均与当前沙箱 DSH 实例匹配。
2. 被调试插件只能通过当前运行时公开的 `llm` 服务读取 provider/model 目录；沙箱模式与正常模式遵循同一服务契约。
3. 确保调试运行的模型目录与同一个沙箱实例内 Composer、设置页面所用的目录一致，而不是与外层宿主目录碰巧一致。
4. 对服务未注册、远程连接失败、目录为空、provider 读取失败、返回结构无效分别给出可诊断结果，不将服务缺失伪装成格式错误或空目录。
5. 宿主 profile/settings、宿主模型目录、宿主凭据以及其他 session 不被调试操作修改或污染。
6. 保留现有 session-owner 授权、danger-full-access 审批、路径约束和凭据保护边界。

### 非目标

- 不把沙箱设置或模型选择写回宿主设置。
- 不让被调试插件读取 `models.json`、overlay 或 `.credentials.yaml`。
- 不复制沙箱 profile/目录/凭据回宿主，也不新增宿主与沙箱间的目录同步协议。
- 不改模型智能测试插件的模拟评测逻辑，不调用模型推理，不新增 endpoint 探测。
- 不把该开发工具描述或改造成能抵御恶意本地代码的 OS 安全沙箱。
- 本需求阶段仅评审和形成文档；不修改插件实现、不运行构建/测试、不启动 sandbox 或浏览器验证。

## 4. 需求说明

### FR-1：完整插件挂载

启动沙箱时，系统须依据已绑定包的公开 package manifest/导出信息，将被调试插件作为该沙箱实例的一部分加载，而非只假定插入 Host 主入口即可满足完整插件需求。Host 和 Client 入口、Client 注入依赖、插件标识必须一致且可解析。不得要求目标插件为沙箱专门维护另一份实现或模型读取协议。

若包清单缺失、入口无效、Client entry 无法解析或插件注册失败，启动状态必须显示可定位的失败原因；不得报“启动成功”后留下不完整的 UI/service。

### FR-2：沙箱内公开模型服务

目标插件在沙箱中读取目录时，调用所在沙箱实例的公开 `llm.listProviders()` 和 `llm.listModels(provider)` 服务。服务必须来自当前沙箱 DSH 运行时。不得由外层 Host 代读后伪装成沙箱目录，也不得让 Client 直接读配置文件。

模型面板若继续提供选择/注入能力，必须清楚区分“宿主目录用于选择注入”与“沙箱运行时最终可见目录”；优先让选择数据明确成为沙箱配置输入，并以沙箱启动后的 `llm` 实际结果作为运行时真相。选择的是配置意图，不等同于模型可用性保证。

### FR-3：服务错误语义

插件 UI 至少区分以下状态，并呈现可操作、不过度泄露秘密的错误：

- 远程 Host service 未注册：`当前运行时不可用：模型目录服务未注册`（或经评审确认的等价文案）。
- 远程连接失败/超时：显示连接失败，可重试；不得作为空目录处理。
- `llm` 服务缺失：显示当前运行时的模型目录服务不可用。
- provider 列表为空：显示明确的空目录状态。
- 单个 provider 加载失败：保留其他成功 provider，并标出失败项；不泄露可能含 header、token 或内部地址的底层异常。
- 返回值结构无效：仅此情况归为目录格式无效。

异常信息可保留安全错误码或诊断 ID；敏感字段和凭据值不能返回浏览器或写入可见日志。

### FR-4：状态与配置隔离

沙箱 overlay、选中模型状态、runtime 配置和凭据继续按当前 session 与 workspace 隔离。插件启动、停止、重启和解绑均不得修改宿主设置文件或宿主 LLM service 状态。停止或清理时只清理该 session sandbox 管理的临时运行状态，不触碰用户原有文件。

凭据在需要时只从现有安全 Host 能力解析，并只写入对应 sandbox runtime；浏览器响应、Remote payload、日志、错误信息和普通 overlay 不得包含密钥值。是否沿用当前“停止后删除凭据文件”的生命周期需实现方案确认，并保持现有行为，除非后续安全评审决定更改。

### FR-5：失败可观测与恢复

Host/runtime 启动日志和面板状态应能区分：Host 加载失败、Client 资源/注册失败、Remote service 不可用、LLM service 不可用、目录查询失败。提供重试或重新启动路径；不得通过伪造 provider/model 掩盖错误。

## 5. 最小验证与验收标准

按用户提出的最小验证边界，以下四项全部通过方可认为问题关闭：

1. 在沙箱运行时调用 `llm.listProviders()`，能够看到预期注入且实际可路由的 provider；逐 provider 调用 `llm.listModels()`，与沙箱设置/Composer 的可见模型一致。若模型受路由规则影响，应记录差异及其规则，不能只比较持久化选择文件。
2. 将一个同时具有 Host service 与 Client UI/Remote 调用的插件挂入沙箱；确认 Host service 注册、沙箱 Web boot manifest 含 Client 入口、Client 页签/Slot 实际挂载，且该 UI 的 Remote 请求到达同一个沙箱 Host 实例。
3. 启动、使用和停止沙箱前后，对比宿主 profile/settings 和宿主模型目录，确认没有变化；确认另一 session 的绑定、运行时及模型状态不变。
4. 停止沙箱后，确认临时 overlay、runtime 配置和凭据仅位于本 session 的 `.dsh/plugin-dev/<sessionId>/` 管理目录；凭据权限与清理行为符合既有策略，不向宿主目录回写。

附加验收：服务缺失、远程不可达、空目录、provider 部分失败和无效响应各有独立状态；无假模型回退；凭据不出现在浏览器、Remote 结果、overlay 或日志。

测试前置：按目标包 README 现有验收规则，测试、冒烟、集成验证、截图和浏览器回归须先向用户提交范围、方法与预计耗时并获批准。本需求文档不代表已获测试授权。

## 6. 实现约束与建议

- 修改范围以 `packages/dsh-plugin-dev-sandbox` 的 overlay/启动流程、插件 manifest 解析、Host/Client 装载契约和相应错误状态为主；仅在确认目标插件错误分类属于其自身实现时，才提出最小兼容修正。
- 优先复用 DSH 公开插件 manifest、Loader、Client boot 与 Typert Remote 机制，不手工拼造第二套远程协议，不解析 DSH 内部配置文件格式。
- 明确插件作为 package 加载时，sandbox 启动器是否能解析其 Client 入口、注入声明和资源路径；若现有 `file://` overlay 机制不能覆盖，需先验证允许的 Loader 表达和包解析边界，再选最小扩展。
- 外层“模型选择/凭据复制”是配置注入路径，不是沙箱模型目录 API。需求实现不得无意中将外层 `llm` Service 对象跨进程注入沙箱。
- 只在 session runtime 中添加目标调试插件，不对宿主 profile 进行全局安装或启用；沙箱停止/销毁范围应由 session 目录的所有权决定。

## 7. 风险与待澄清事项

1. **复现信息缺失**：请在实施前补充实际操作步骤、预期与实际表现、UI/Remote 错误文案、是否在沙箱打开插件面板，以及 sandbox Host/client 日志。当前结论仅基于目标架构和代码检查。
2. **正常模式对照**：确认模型智能测试插件在宿主正常模式是否已成功读目录；当前其 README 写明未安装且未做集成/浏览器测试，因此“与正常模式等价”目前是设计目标，不是回归基线。
3. **Client 装载契约**：确认 DSH 当前 `--patch` 对 file URL 插件行如何解析目标包的 `dsh.client` 声明与注入依赖；不能从 Host 入口成功加载推断 Client 已正确挂载。
4. **模型来源语义**：面板选择目前读外层 Host `llm` 并把可配置 provider profile 复制/patch 进 sandbox。需要确认是否保留该 UX；即使保留，运行中插件必须只读沙箱自身 `llm` 服务，并允许它与配置选择有差别（如模型路由/配置无效）。
5. **清理边界**：停止实例与删除 session 运行目录不是同一操作。验收应明确停止时仅移除运行凭据/进程，解绑是否保留 binding、models 和 overlay 等按现有数据生命周期执行，不应误删整个 session 工作区。
6. **安全表述**：本功能的“隔离”仅为进程/profile/config 隔离；调试插件以当前用户权限运行。不得对用户承诺阻止恶意插件访问其有权限的文件或网络。
