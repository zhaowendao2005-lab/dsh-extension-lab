# 逐线交付插件：一端读懂版

这份说明只讲插件本身怎么工作。实验底座另算：实验者可以用 DSH headless 启动同一个插件，记录事件并生成 HTML 报告；真实用户在 DSH GUI 中使用插件时，不会启动 headless，也不会看到或依赖实验报告。

## 一、插件到底负责什么

用户只给一段原始需求。插件完成四件事：

1. 把需求整理成“要交付的结果”。
2. 把结果拆成若干条能独立完成、独立判断的交付线。
3. 让不同 Agent 施工；哪条线先完成，哪条线先验收。
4. 把每条线的结果和整体验收结果返回给用户。

插件不负责：

- 启动 DSH headless；
- 统计实验用的时间、token、成本或并发；
- 生成实验 HTML/report；
- 因为正在做实验而改变生产流程；
- 给自己增加一个最后统一审查 Agent。

生产链路只有：

```text
用户原始需求
  -> 需求和事实整理
  -> 单元、接口、验收卡锁定
  -> 各单元施工
  -> 各单元独立取证和判定
  -> 交付用户结果
```

测试链路在插件外：

```text
实验 driver
  -> dsh --profile headless
  -> 同一个插件
  -> 插件结果/公开事件
  -> 实验 driver 计算指标、保存重放、生成 HTML report
```

headless 是实验 driver 选择的启动方式，不是插件的运行模式。

## 二、什么才算一个“单元”

单元不是一个文件、一个按钮或一个 Agent。单元是：**用户可以实际使用的一项结果，并且可以用一张卡独立判断它是否完成。**

例如一个“数据导入”需求，合理的单元可能是：

- 导入并保存一份数据；
- 查看导入结果并返回；
- 导入失败时显示可恢复的错误。

不合理的切法是：

- 前端单元；
- 后端单元；
- `parser.py` 单元；
- “点击导入按钮”单元。

因为这些不是用户可独立使用的结果，完成它们并不能说明需求完成。

每个单元必须有六个东西：

| 内容 | 含义 |
| --- | --- |
| 结果 | 完成后用户得到什么 |
| 输入 | 从哪里开始、依赖哪些已确认事实 |
| 输出 | 哪个候选版本和哪些接口可供下游使用 |
| owner | 谁负责产生这个结果 |
| 验收卡 | 真实动作、预期观察、证据来源 |
| 边界 | 明确不负责什么，交给哪条线 |

锁定 Spec 时，插件拒绝三类坏单元：没有用户结果、没有独立证据、责任边界无法说明。

## 三、单元之间会不会互相踩

会，所以不能只靠提示词说“不要冲突”。插件在派工前做三层约束。

### 1. 写入不重叠

每个单元拿到自己的写入租约。两个单元不能同时拥有同一份可变业务产物的写权限。

共享基础代码、共享数据结构或共享配置必须先指定一个 owner。其他单元只能消费已发布的接口，不能顺手修改共享部分。

```text
共享接口 owner -> 发布版本化接口
单元 A -> 消费接口 A
单元 B -> 消费接口 B
```

如果两个单元都必须改变共享接口，插件不并发派工，而是先生成一个“接口变更单元”，完成后重新锁定受影响的卡。

### 2. 读依赖必须写清楚

单元可以读取别人的已发布制品，但依赖必须写成具体关系：

```text
B 等待 A 发布 user-record@2
```

不能写成“B 等 A 差不多完成”，也不能把所有单元都挂到一个公共底座后面。

### 3. 跨单元行为提前成为一条线

如果问题只有把 A 和 B 接起来才会出现，那么它不能留到最后再找一个共享 Reviewer。Spec 阶段就要生成一条明确的“边界单元”或把这段行为归给一个明确 owner：

```text
A 的保存结果
  -> B 的读取流程
  -> 这是一个独立的跨边界用户结果
  -> 有自己的 owner、卡和证据
```

这条线不是所有单元完成后的总审查，而是图中一开始就存在的真实交付线。它的输入是 A 的已发布候选，B 的实现可以继续，但边界线在依赖满足后立即执行。

因此“单元各自通过”与“组合后仍然可用”分别有证据：

- 单元卡证明 A、B 各自的结果；
- 边界卡证明 A→B 的真实使用；
- 全局交付只汇总这些已经定义好的卡，不临时新增一个大而模糊的回归。

## 四、判定失败后谁修

判定器不负责修复。它只负责把失败说清楚；插件根据失败包把任务发给唯一责任 owner。

每次拒绝必须包含：

```json
{
  "verdict": "FAIL",
  "unitId": "import-and-review",
  "candidateId": "candidate-17",
  "checkId": "record-match",
  "expected": "提交后显示刚导入的记录及其数量",
  "observed": "页面显示成功，但记录列表为空",
  "evidenceRefs": ["run-snapshot-42", "console-log-8"],
  "faultDomain": "implementation",
  "repairOwner": "unit-owner-import-and-review",
  "minimalRepair": "修复提交成功后记录列表未刷新，不改变导入接口和验收卡",
  "replay": "从固定起点重新执行 checkId=record-match"
}
```

`faultDomain` 决定责任：

| 失败类型 | 修复责任 |
| --- | --- |
| 业务行为确实不符合卡 | 对应施工单元 owner |
| A 发布的接口与锁定契约不一致 | 发布该接口的 owner；必要时让受影响消费者新建 attempt |
| 卡、Spec 或切分本身互相矛盾 | Spec/契约 owner；不能让施工 Agent 自己改卡 |
| 选择器、Runner、证据采集出错 | 验收适配器/Runner owner |
| 上游不可用、权限不足、证据不完整 | `NO_DECISION`，由环境或侦查 owner 处理，不算业务 FAIL |
| A→B 组合行为失败 | 预先登记的边界单元 owner；不能在 A、B 之间互相甩锅 |

模型 Judge 只能给观察和理由，不能指定一个它没有权限验证的 owner。Host 根据图中的归属和证据域计算 `repairOwner`。

## 五、怎样尽量一次完成，而不是反复拒绝

关键不是让 Judge 多试几次，而是让第一次拿到足够好的输入，并把一次失败限制在很小的范围。

### 派工前一次准备

锁定施工前，插件强制生成并检查一个“完成包”：

- 用户结果和不可变验收卡；
- 输入、输出和接口示例；
- 已验证事实及其有效范围；
- owner 和唯一写入范围；
- 依赖和禁止事项；
- 真实起点到结果的完整验收旅程；
- 编译/装载入场命令（适用时）；
- 失败后应归属的 fault domain。

完成包不由施工 Agent 自己编写，也不在施工中改变。这样施工 Agent 第一轮拿到的是“做什么、做到哪里、如何被观察”，而不是只有一句模糊任务。

### 一次验收顺序

1. Host 检查候选是否属于正确的 run、版本和写入租约。
2. 先做确定性检查：能否装载、真实入口是否存在、关键值/副作用/错误日志是否符合。
3. 确定项没有失败时，才把剩余语义证据交给一次 Jev 或 DS41。
4. 生成一个结构化决定：`PASS`、`FAIL` 或 `NO_DECISION`。
5. `PASS` 立即提交该线交付；`FAIL` 生成一份最小修复包；`NO_DECISION` 修复证据或环境，不让实施 Agent 盲改业务。

语义 Judge 每个候选最多一次。没有“Judge 不喜欢所以换个问法再问一次”，也没有“先改代码再偷偷重判”。这保持了实验可归因，也防止无限循环。

### 失败后的有限修复

默认每条线只预留 **一次有边界的修复 attempt**，且只能改 `minimalRepair` 指定的范围。修复后只重放受影响的完整旅程，不把整个项目推倒重来。

- 修复后通过：记录 `PASS_AFTER_REPAIR`，继续交付；
- 修复后再次同一检查失败：终止该线为 `FAIL`，把证据交给用户；
- 修复期间发现卡或接口错：转 `SPEC_BLOCKED`，由契约 owner 修正版本，不能让施工 Agent无限试。

对于高风险缺陷，例如数据丢失、权限越界、错误成功，默认不自动修复第二次，直接停止并要求人工决定。一次修复额度不是为了掩盖问题，而是防止“反复拒绝”吞掉整个交付时间。

## 六、为什么组合结果可信

插件在交付事务前不做一个笼统的“看起来没问题”判断，而是检查四个闭包：

1. **需求闭包**：每项必需需求至少映射到一张验收卡。
2. **接口闭包**：每条依赖都指向已发布且版本匹配的制品。
3. **证据闭包**：每张必需卡都绑定当前候选的真实证据。
4. **修复闭包**：每个 FAIL/NO_DECISION 都有明确 owner 和未完成状态，不能被汇总器吞掉。

四个闭包都满足，才可以提交交付事务。一个单元通过不会自动把下游标成通过；下游必须消费实际发布的候选并走自己的卡。一个单元失败也不会拖死无关单元，只有依赖它的线被阻塞。

## 七、插件和实验底座的最后边界

插件生产时只返回：

- 当前 run 的状态；
- 每条线的结果、证据引用和修复原因；
- 是否可以提交交付；
- 交付制品或明确缺口。

实验底座才保存：

- headless 启动参数和 stdout/stderr；
- 多次运行、分组和随机化；
- TTA、token/cache、成本、并发和停止拖尾；
- 影子判定与金标比较；
- HTML 实验报告和重放索引。

生产插件不会因为没有这些实验文件而改变行为。实验底座可以测插件，但不应被插件依赖。
