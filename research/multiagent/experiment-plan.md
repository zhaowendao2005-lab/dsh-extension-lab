# DSH 多智能体提速实验方案

## 1. 实验要回答什么

实验目标不是证明“测试越多越好”，也不是证明“并发 agent 越多越快”，而是验证：在用户认可的交付质量不下降的前提下，DSH 能否更快到达可交付状态，并降低用户等待、无效回归和总成本。

需要分别回答四个问题：

1. **前端何时可以停？** 用户满意、核心业务路径通过、关键视觉/无障碍问题清零后，继续跑全量回归是否仍能发现有价值的问题？
2. **DS41 代码落成是否适合并发？** 与单 agent 相比，2/4 个有明确文件/模块边界的 DS41 子代理，能否更快得到一次集成即可验收的实现？
3. **测试怎样并行才有效？** 以 Playwright CLI 按业务线跑 E2E、观察真实错误和日志，并行验证是否比反复跑大而全的回归更快、更会发现重要问题？
4. **时间预算能否作为“压力维度”？** 让 agent 持续看到剩余预算并据此在继续调查与开始交付之间切换，能否缩短长尾，又不导致仓促交付？

核心定义：**测试是证据和风险控制手段；用户目标达成且验收条件满足，才是完成目标。**

## 2. 依据与实验边界

本机 303 个会话的初步分析（143 个 root、160 个子代理）提供了假设，不是因果结论：

- 子代理活跃时间 90.6% 在模型生成，工具 5.6%；步数 p50=26、p90=88、最大 225；单步延迟 p50=9.3 秒、p90=31.5 秒。
- root 在子代理运行时有 19.4% 时间处于等待/轮询；`wait_agent` 27/59 次超时。
- 只有 24/160 个子代理在结束前至少 60 秒发过中途消息；完成通知 p90=3,355 字符，最大 36,648 字符。
- 用户有多次要求“够了、收回子代理、汇报”，说明现有目标函数没有清晰的停止判据。

来源和口径详见 [多智能体机制研究报告](report.md) 与 [本机会话指标](session-metrics.json)。实验将 DSH 版本、DS41 的精确模型 ID、模型参数、工具权限和运行环境固定；DS41 的单价低是开展并发实验的动机，不预设并发一定节省总成本或提高质量。

## 3. 先定义“可以交付”

每个任务开跑前，由不参与执行的人冻结一张验收卡。验收卡不得在看到结果后放宽。

| 验收项 | 前端任务 | 后端/集成任务 |
|---|---|---|
| 用户目标 | 目标用户、要完成的动作、明确不做的事 | 业务角色、输入、状态变更、预期输出 |
| 核心路径 | 1–3 条主要交互路径及期望状态 | 1–3 条真实端到端业务线（UI/API→服务→存储/外部依赖） |
| 质量底线 | 无阻断交互问题；关键文案/布局与需求一致；关键视口截图可审 | 数据/副作用正确；权限与错误处理符合需求；关键失败可诊断 |
| 自动化证据 | 目标路径 smoke/E2E；按改动风险选择 lint/typecheck/针对性测试 | Playwright CLI 或项目既有 E2E 按业务线执行；核对 UI、API/状态及日志 |
| 交付判据 | 盲评用户体验评分 ≥4/5，核心路径通过，未解决的 P0/P1=0 | 核心业务线全部通过，数据状态正确，P0/P1=0，失败时有足够日志定位 |
| 停止判据 | 达到以上条件后停止广泛回归；仅在高风险改动/新缺陷证据下扩测 | 业务线通过且风险检查完成即交付；不把全量回归次数作为目标 |

P0/P1 定义在实验开始前写清楚。P0 = 数据丢失、安全/权限边界破坏、主要流程不可用；P1 = 主要用户路径错误或结果错误。P2/P3 进入后续 backlog，不自动阻止交付。

前端评价由至少 2 名不了解实验组别的评审者独立打分；报告均分、差值和分歧。主观分数不能覆盖客观路径失败或 P0/P1。

## 4. 实验指标

### 主指标

1. **Time-to-Accepted (TTA)**：从任务开始到验收卡全部满足、评审接受的墙钟时间。未完成任务按截止时间右删失，不能当作“很快完成”。
2. **验收成功率**：任务最终达到验收卡的比例；单次通过率与重复运行稳定率分开报告。
3. **盲评质量**：前端体验 1–5 分；后端正确性/可诊断性分别按 1–5 分，报告均值与 95% 置信区间。
4. **每个被接受交付的总成本**：模型输入/输出 token 与费用、E2E/测试执行时间、人工评审/修复时间都计入。不能只算 DS41 token 费用。

### 次指标与护栏

- 第一次提交即通过核心验收的比例（first-pass acceptance）；第一次编译/typecheck/E2E 通过率。
- 用户要求的重复回归次数、无新增缺陷的回归次数、每次回归发现的有效问题数。
- 发布后 7 日内 P0/P1、验收后回滚/返工率；P2/P3 单列。
- E2E 业务线通过率、注入缺陷召回率、误报率、平均诊断时间、日志足以定位的比例。
- 并发实现：总墙钟、总模型成本、合并冲突率、跨代理修改同一文件次数、集成返工次数、最终 diff 的人工返工分钟数。
- 多次运行稳定性：pass@3（3 次至少成功 1 次）和 pass^3（3 次全成功）；对交付可靠性优先看 pass^3。此类重复试验能发现单次结果掩盖的随机性，见 [Agent Evaluation Survey](https://arxiv.org/html/2507.21504v1) 与 [τ-bench 指标综述](https://www.honeyhive.ai/learn/agent-evaluation-metrics)。

### 预先写下的成功阈值

以下是实验决策门槛，不是对结果的预测：

- 提速方案 TTA 中位数至少降低 **20%**，且 p90 不恶化；目标是 p90 降低 **30%**。
- 验收成功率相对基线下降不超过 **5 个百分点**；前端盲评均分下降不超过 **0.3/5**。
- 新增 P0=0；P1 率不得出现有实际意义的上升。若出现任何新增 P0，立即暂停该组并复盘。
- 每个被接受交付的总成本不增加超过 **10%**；如果为明显更快而增加成本，单独报告速度/成本前沿，不把“便宜模型”直接等同于“便宜交付”。
- 并行测试在不降低关键缺陷召回率超过 **5 个百分点** 的情况下，验证时间至少减少 **25%**。

## 5. 实验 A：前端“满意即交付”与测试停止规则

### 假设

按验收卡运行核心用户路径、检查关键视口并得到盲评 ≥4/5 后停止；相比每轮改动后继续全量回归，TTA 更短，而质量和 7 日缺陷率不劣。

### 分组

- **A0 当前流程**：按团队现行做法测试/回归，记录每轮测试的新增有效发现及时间；不得故意阻止正常交付。
- **A1 验收门控**：核心路径 + 风险相关的针对性检查 + 盲评。一旦达到停止判据，停止广泛回归；若出现新证据或高风险触发条件，允许扩测并记录原因。

### 样本与流程

先选 12 个历史/新前端任务试跑（6 个小视觉或交互调整、6 个完整用户流程/状态改动），完善验收卡和评分一致性。确认阶段至少 30 个成对任务；每个任务用隔离分支和同一基线，随机分配 A0/A1 的执行顺序，评审者盲评。约四分之一任务做第二次独立运行，检查模型随机性。

### 主要观察

- 达到盲评和核心路径标准所需分钟数；达标之后额外回归耗时。
- 达标后每 30 分钟全量回归发现的 P0/P1/P2 数量；“发现问题”按复现且与任务相关才计有效。
- 盲评均分、核心路径通过率、7 日 P0/P1/P2 返工率。
- 如果达标后额外回归基本只发现 P2/P3 且无 P0/P1，则支持缩减；若出现真实 P0/P1，检查风险分类是否漏项，不能简单归结为“测试本来没必要”。

### 停止规则

达到验收卡就可交付；不要求把所有测试跑绿。测试失败只有在可复现且与需求/风险相关时才阻止交付。环境不稳定、无关旧失败要单独登记，不无限重跑。

## 6. 实验 B：DS41 一次成型与代码实现并发

### 假设

对于可独立拆分的任务，明确定义接口、文件所有权和验收卡后，2–4 个 DS41 子代理一次成型可缩短 TTA；收益会被集成冲突、代理重复探索和修复成本抵消的任务也应被识别出来。

### 组别（阶段式筛选，避免一开始就铺满组合）

- **B0 单 agent 迭代基线**：一个 DS41 agent 完成任务，允许按当前常规流程修复。
- **B1 单 agent one-shot**：一个 DS41 agent 按冻结的实现契约直接交付；只允许一次受控修复机会，记录是否使用。
- **B2 2-agent one-shot**：任务分为 2 个有边界的模块/工作包，各自独立提交；lead 做一次集成。
- **B4 4-agent one-shot**：同上，分 4 个边界；只用于足够可并行任务。

不强行把不可分任务拆成 4 份。样本按“可并行性”分层：高（独立模块/文件）、中（共享接口但能先冻结契约）、低（强耦合单模块）。低可并行样本主要比较 B0/B1，作为并发负对照。并行组限制写入边界；共享接口只由 lead 或指定 owner 修改。

### 样本与流程

选 12 个试点任务（前后端各半，含高/中/低可并行性），每组先跑 1 次用于发现协议问题。确认试验在试点后选择有收益的对比，至少 30 个匹配任务族；对 B0/B1/B2/B4 运行时使用隔离 worktree、相同代码基线、相同 DS41 版本和工具权限。任务顺序和运行时段随机化；至少 25% 任务用独立 seed 重跑。若工作包边界或需求在中途变更，该任务标记偏离方案并保留，不得悄悄剔除。

### 关键指标

- first-pass acceptance 与最终验收成功率分开；one-shot 的“一次成型率”定义为：第一次集成后达到验收卡，未发生代码修改型返工。
- TTA、每次成功交付总费用、最终人工返工时间。
- 合并冲突率 = 需人工解决的冲突数 / 并行任务数；重叠写文件率、跨代理接口不一致数。
- 代理数从 1→2→4 后的加速比 = 单 agent TTA / 并行 TTA；效率 = 加速比 / agent 数。同步记录模型并发限流/排队时间，避免把 provider 拥塞归咎于任务分解。
- 失败分析分类：契约遗漏、模型未遵约、共享文件冲突、需求不适合并行、工具/环境错误、测试发现真实缺陷。

### 决策规则

只有在 TTA 至少下降 20%、验收质量通过非劣门槛、每个成功交付总成本不高于基线 10%、人工集成/返工没有吞掉节省时间时，才推广该并发度。若 B2 有效而 B4 无效，应采用按可并行性动态选择 1/2/4，而不是固定最大并发。若 B1 的 first-pass 质量明显下降，保留一次定向修复，不把“one-shot”变成拒绝纠错的硬限制。

## 7. 实验 C：按业务线的 E2E 与并行验证

### 假设

在后端和全栈任务上，多个只读验证代理分别按 Playwright CLI 执行业务线、检查状态副作用与错误日志，可以更快暴露端到端缺陷；它们应作为交付证据，不是继续盲目扩张回归范围的理由。

### 验证通道

每个任务先冻结 2–4 条业务线。例如“登录→创建订单→确认落库”“修改权限→无权限用户访问被拒绝”“失败请求→UI 有错误态且服务端有可定位日志”。浏览器状态、账号和测试数据隔离，避免并行测试互相污染。

- **C0 序列回归**：现有测试策略/测试责任人串行执行，记录耗时和问题。
- **C1 并行 E2E**：2–3 个验证代理并行，各自负责一条独立业务线；至少一条从 UI 经 API 到最终状态验证。一个代理检查日志和错误可诊断性。所有验证代理只读代码/环境，不和实现代理同时改代码。
- 对两组执行同一套**预先植入的可控缺陷**：例如状态未持久化、权限校验遗漏、错误态丢失、关键日志字段缺失。注入缺陷只在实验副本中，修复前先盲测，避免评审者知道位置。

### 样本与指标

试点 8 条业务线、每线 3–5 个缺陷变体。确认阶段至少 20 个业务线场景，每种风险至少 10 个注入变体；样本不够时将召回率报告为探索性结果，不声称优于基线。

- 关键缺陷召回率 = 首轮验证发现的已注入 P0/P1 数 / 注入 P0/P1 总数；P2/P3 另报。
- 误报率 = 被报告但无法复现或与任务无关的问题 / 全部报告问题。
- 验证墙钟、首次可诊断失败时间、日志可定位率、Playwright 用例有效通过率。
- **Playwright 不通过时的闭环**：保存 trace、console/network 错误、服务端日志和关联 ID；如果证据不足，再补最小日志，然后重跑受影响业务线，而不是立即重跑全部套件。

### 注意

Playwright CLI 是业务线验证工具，不替代所有 unit/typecheck/静态检查；针对改动范围的快速确定性检查仍可保留。比较的是“有边界的必要证据”与“无判据的反复回归”，不是 E2E 对所有测试的替代。

## 8. 实验 D：剩余时间作为压力维度

### 假设

只告诉 agent “必须在 X 分钟完成”可能导致仓促交付；把剩余预算和阶段策略持续放入决策上下文，能促使它合理转向交付，同时保持验收质量。

### 组别

- **D0 无预算**：现行流程，不提示截止时间。
- **D1 固定硬截止**：告知截止时间，到点要求交付；中间不注入阶段策略，用于区分“压力”本身与“预算管理”。
- **D2 动态预算**：每轮/关键决策点显示剩余时间，并按阈值驱动行为：
  - High（>50%）：允许调查与拆分；
  - Medium（25–50%）：不再派生非必要代理，聚焦验收卡缺口；
  - Low（10–25%）：停止扩展研究，要求子代理提交部分结果，lead 开始综合；
  - Critical（<10%）：收回非关键代理、只保留修复/交付步骤；到截止后明确列出未完成项并交付当前结果。

### 预算标定

先用 12 个试点任务测量 D0 的 TTA，按任务类别建立基线分布。确认阶段以同类任务 D0 的 p50 作为正常预算 `B`；D1/D2 使用相同 `B`，另对 20% 的任务使用 `0.75B` 做紧预算压力测试。不可拿单一“10 分钟”覆盖难度差异巨大的任务。预留预算需包含集成、E2E 与最终回复，不能把全部时间分给调查。

### 指标与安全护栏

- 预算内达到验收卡的比例、TTA、中位数/p90 剩余时间、预算超时比例。
- 阶段转换是否合理：High→Medium 时剩余未答关键问题数；Low 时是否已开始整合；Critical 时是否能给出有证据、标明未完成事项的交付。
- 盲评质量、验收成功率、P0/P1、返工率、成本；预算内完成但验收失败不计成功。
- 用户目标被压缩/改变的比例，必须由用户授权或在最终交付中清晰声明；agent 不可自行把原目标偷换成更易完成的目标。
- 在 D1/D2 出现新增 P0，或质量越过非劣界限即暂停紧预算组；逐案区分预算过紧、进度估算差、任务不适合受限执行。

### 扩展研究 vs 结束交付的决策信号

不要单靠 LLM 的“我觉得够了”。组合使用：

1. **确定性验收状态**：未通过的关键业务线、待验证副作用、P0/P1 清单。
2. **剩余预算**：剩余时间是否覆盖至少一轮 E2E/修复/交付。
3. **边际价值判断（Jev/快速 LLM）**：只问短问题，例如“继续调查是否可能改变验收结论或修复 P0/P1？输出 1/0。”。只影响优先级，不可单独批准危险操作或宣布成功。
4. **迟滞**：连续两个独立检查都判定“没有会改变验收的关键未知项”，且硬验收条件已过，才从继续调查切换到收敛。出现新失败证据立即回到修复。

## 9. 实验执行与统计

### 共同控制变量

- 固定 DSH 版本、DS41 模型 ID/版本/参数、系统提示、工具权限、仓库提交、依赖和 Playwright 环境。
- 每次运行使用干净隔离分支/worktree；清空临时数据库并使用独立账号和测试数据。
- 任务说明、接口契约、验收卡在各组完全一致；除实验变量外不允许 lead 临场给某组额外提示。
- 随机化任务顺序/运行时段；记录模型 provider 排队、重试、限流、网络故障和人工介入。
- 评审者看不到组别；人工介入、提示次数和用时全部入账。

### 分析方法

- 同一任务族成对比较；报告中位数、p90、差值/比值与 95% bootstrap 置信区间，不只报均值。
- 运行耗时使用 log 比率或配对差值；失败/超时单列，并做把失败视为超时上限的敏感性分析。
- 对通过率、缺陷率报告绝对百分点差与置信区间；任务层级 bootstrap，避免把同一任务的多次 seed 当成独立任务。
- 试点用于估计方差和修订流程，不用于宣布胜出。完成试点后冻结验收卡、阈值和分析方案，再开确认阶段。
- 小样本阶段结果只能决定“是否继续扩大实验”，不能作为质量已证明非劣的结论。

### 样本量建议

建议分两阶段而非一次性全因子：

1. **校准试点**：12 个前端 + 12 个后端/全栈任务；先跑流程，估计任务间方差、DS41 限流和验收评审一致性。
2. **筛选阶段**：每个主题 12–16 个代表任务；B 组先筛 1/2/4 并发，D 组先筛预算策略。只淘汰明显更慢、明显更差或成本更高的配置，不做强结论。
3. **确认阶段**：对每个主要结论至少 30 个成对任务族，且至少 25% 任务复跑；若试点中配对 log(TTA) 标准差约为 0.5，检出 20% 提速通常需要约 60 个任务族（近似公式 `n ≈ ((1.96+0.84)×σ / |ln(0.8)|)^2`）。因此先用试点方差重算样本，可能需要 30–60 个以上；不要把多 seed 替代任务多样性。

若预算不足以支撑确认样本，明确称为“内部可行性试验”，报告效应区间与残余不确定性，不宣布统计胜出。

## 10. 运行量、周期与决策门

### 预计实验规模（首轮可调整）

- 任务集：12 个前端任务、12 个后端/全栈任务校准；确认阶段根据方差扩充到每个关键对比 30–60 个任务族。
- 代码代理筛选：每个任务对比单 agent 迭代、单 agent one-shot、2 并发 one-shot、4 并发 one-shot；只对可并行层使用高并发组。
- E2E：先 8 条业务线试点，至少 20 条确认业务线；每条至少 2 个核心场景，并植入 3–5 类实验缺陷。
- 时间预算：每个主题 D0/D1/D2 对比；正常预算按任务类型 p50 标定，紧预算仅覆盖 20% 的任务。
- 对任何正式胜出配置，最少 25% 独立 seed 复跑；成本与时间均计完整 agent 树和测试环境。

### 周期建议

- 第 1 周：冻结任务集、验收卡、风险等级、脚本和评审 rubrics；对历史任务做回放演练。
- 第 2 周：校准试点、检查随机化/隔离/日志完整性，估算样本方差并冻结方案。
- 第 3–4 周：筛选并行度、停止规则和预算策略；每周复盘失败案例，但不改动确认期口径。
- 第 5 周起：只对候选胜出配置做确认；汇总 7 日返工/缺陷信号后决定是否灰度。

### 灰度/回滚门

1. 试点：仅内部任务，不自动中断 agent，不自动跳过现有安全检查。
2. 灰度：选择 10% 可回滚、低风险任务；用户/lead 可随时要求继续测试或停止子代理。
3. 推广：必须通过速度、验收质量、P0/P1、成本四道门；并行或预算策略未通过非劣质量门则不推广。
4. 紧急回滚：任意新增 P0、明显错误地终止关键子代理、核心流程验收率下降 >5 个百分点，立即停用对应策略并保留日志复盘。

## 11. 预期产物

- 冻结的前端/后端验收卡模板与一组可重复任务集。
- 每个任务的 session trace、agent 树、TTA、完整成本、测试证据与盲评结果。
- 并发拆分和文件所有权模板；适用/不适用并行的任务特征。
- E2E 业务线清单、Playwright trace、注入缺陷召回/误报结果、日志诊断缺口清单。
- 对动态预算策略的推荐阈值；按任务难度给出的建议预算，而不是全局固定超时。
- 最终决策：保持现状、按任务类型采用 1/2/4 agent、启用验收门控、启用动态预算，或继续收集证据。
